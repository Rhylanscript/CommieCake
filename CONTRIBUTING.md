# Contributing to Commie Cake

Thank you for taking the time to contribute! This project is a modular, web-based sorting visualizer. Following these guidelines helps ensure your additions merge smoothly.

## Getting Started

1. **Fork the Repository** on GitHub.
2. **Clone your fork** locally:

   ```bash
   git clone https://github.com/you/your-fork
   ```

3. **Create a feature branch** off `main` for your changes:

   ```bash
   git checkout -b feat/your-feature-name
   ```

4. **Run a Local Server** to test your changes. I recommend using the VS Code **Live Server** extension pointed at the root directory.

## Project Architecture

Please respect our modular file structure when adding code:

- `public/algorithms/`: Every sorting routine must live in its own file here as a standalone ES Module generator function.
- `public/js/main.js`: Strictly reserved for DOM event listeners and setup initialisation.
- `public/css/...`: CSS rulesets belong in the appropriate files.

## Code Style Guidelines

- **ES Modules:** Use modern JavaScript syntax (`import`/`export`). Always include the explicit `.js` file extension in your relative paths.
- **No Inline CSS:** All layout rulesets belong in external stylesheets. Never use the `style="..."` HTML attribute.
- **Keep Files Under 150 Lines:** If a utility file starts growing too large, split it up into logical modules.
- **Indentation:** All indentation for all filetypes should be 4 spaces as a tab.

## Creating New Algorithms

If you are adding a new sorting algorithm, you **must** follow the explicit design contract detailed in the [algorithm README][algorithm].

## Testing Your Changes

Before opening a Pull Request, open your browser's Developer Tools Console (`F12`) and confirm:

1. There are no uncaught syntax or import path errors.
2. Your algorithm renders individual comparison/swap frames correctly without skipping straight to the end.
3. If your algorithm handles large scales poorly (like Bogo Sort), ensure its ID is added to the `NEVER_FINISHES_AT_SCALE` bypass array in the benchmark logic.

## Submitting a PR

1. Push your branch up to your GitHub fork.
2. Open a Pull Request against this repo's `main` branch.
3. Use clear, conventional commit descriptions (e.g., `feat(algorithm): add cheese sort` or `fix(ui): fix the flux capacitor`).

## Rules on Generative AI

Generative AI is ok to use for code as long as:

1. You understand the code, and are able to explain it.
2. Any code review must be done by a human at least once before being merged to main.
3. Using generative AI to debug is fine.

AI should not be used for:

1. **Designing** - core architecture, complex logic or features.
2. **Lone reviews** - All code review _MUST_ be done at LEAST in part by human.
3. **Testing** - While it is fine for AI to test functionality, the developer is responsible for ensuring they are rigorously testing code.
4. **Assets** - No assets are to be generated by AI, all must either be generated by developers or from online asset libraries.
